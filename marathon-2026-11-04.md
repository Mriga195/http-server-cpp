## L0: IP, ports, TCP; what a socket is
**Learn:** IPv4 vs IPv6, what a port is, TCP vs UDP (when you need reliability vs speed), the 3-way handshake, network byte order (`htons`/`ntohs`), DNS, and what a socket is (an fd that points at a network connection).
**Beej:** ch. 2 (2.1), ch. 3 (3.1–3.3), 5.1 `getaddrinfo`.
**Look around:** `ss -tlnp` (what is listening on your machine), `getent hosts google.com`.

- **Exercise** `exercises/L00-showip.cpp`: takes a hostname as `argv[1]` and prints every IPv4/IPv6 address it resolves to.
  Use: `getaddrinfo`, `inet_ntop`, `freeaddrinfo`, `gai_strerror`. Run: `make ex L=00 && ./build/L00 google.com`
- **Variation** `L00b-showport.cpp`: pass service `"http"`/`"https"` and print the port too.
- **Break it:** print the port without `ntohs` and explain the strange number you get. Pass a hostname that doesn't exist and print the error.
- **Explain back:** Why do we need byte order conversion? What does the handshake guarantee? What is `struct addrinfo` a linked list of?

## L1: File descriptors
**Learn:** an fd is a small int that indexes your process's open-file table. Know 0/1/2, why the kernel hands out the lowest free number, `open`/`read`/`write`/`close`, that `read` can return less than you asked for, `errno` + `perror`. Know the idea that "everything is a file" (sockets too).
**Man pages:** `man 2 open`, `man 2 read`, `man 2 write`, `man 2 close`.

- **Exercise** `exercises/L01-raw-cat.cpp`: your own `cat`: copies a file to stdout using only `open`/`read`/`write`/`close`. No iostream, no stdio for the data. Handle short writes and errors.
- **Variation** `L01b-fd-numbers.cpp`: open 3 files, print their fds, close the middle one, open again, then predict and check which number you get. While it sleeps, run `ls -l /proc/<pid>/fd`.
- **Break it:** open files in a loop without `close` until it fails (`EMFILE`), then compare with `ulimit -n`. Run your cat with `strace ./build/L01 somefile` and read the syscalls.
- **Explain back:** What does `read` returning 0 mean? What does -1 mean? Why can `write` write less than you asked? What happens to fds when the process exits?

## L2: Echo server: socket, bind, listen, accept
**Learn:** the server lifecycle `socket → bind → listen → accept → recv/send → close`. Listening socket vs connected socket (two different fds!), the backlog, `recv` returning 0 when the peer closed, `SO_REUSEADDR`.
**Beej:** 5.2, 5.3, 5.5, 5.6, 5.7, 5.9, 6.1.

- **Exercise** `exercises/L02-echo-server.cpp`: listens on port 9000 and echoes back whatever a client sends. When the client leaves, accept the next one (one client at a time is fine).
  Test: `make run L=02`, then in another terminal `nc localhost 9000`.
- **Variation** `L02b-uppercase-echo.cpp`: echoes the text back in uppercase. Optional: count the clients and greet each one with "you are client #N".
- **Break it:** (1) Kill and immediately restart the server. You get `EADDRINUSE`. Fix it with `SO_REUSEADDR`. (2) Forget to `close` the client fd, connect 5 times, then look at `/proc/<pid>/fd` and `ss -tn`. (3) Connect two `nc` clients at once and see what happens to the second one.
- **Explain back:** Why two fds? What does `listen`'s backlog do? Why does the second client hang? (This answer leads into Lessons 6–8.)

## L3: Client: connect; testing with nc and curl
**Learn:** `connect` (the client side of the handshake), that `nc` can act as either side, `curl -v`, and that HTTP is just text over TCP.
**Beej:** 5.4, 6.2.

- **Exercise** `exercises/L03-echo-client.cpp`: connects to your L02 server, sends each line from stdin, and prints the reply.
- **Variation** `L03b-http-get.cpp`: connects to `example.com:80`, sends a GET request you type out by hand (watch the `\r\n`s), and prints the raw response.
- **Bridge to L4:** run your L02 server and `curl -v localhost:9000/hello`. The server echoes back curl's actual HTTP request. Save it in your notes.
- **Break it:** connect to a port nothing is listening on (`ECONNREFUSED`). Kill the server mid-session: what do `recv` and `send` do (`SIGPIPE`)? Leave out the blank line in your GET request: what happens?
- **Explain back:** What happens on the wire during `connect`? Why does HTTP need `\r\n\r\n`?

## L4 (stretch): HTTP request format and parsing
**Learn:** request line (`METHOD PATH VERSION`), headers, the blank line, body; status line + `Content-Length` in the response; why a single `recv` might not contain the whole request.
**Read:** MDN "HTTP messages" (Beej doesn't cover this).

- **Exercise** `exercises/L04-parse-request.cpp`: a parser for a hard-coded request string (paste the one you captured in L3). Prints the method, path, version, and each header.
- **Server** (first real `server/` code, one job per file): `server/main.cpp` and `server/http_request.hpp/.cpp`. Accept a connection, read until `\r\n\r\n`, parse it, respond `200 OK` with a body and the correct `Content-Length`. Test: `make server && ./build/server`, then `curl -v localhost:9000/` and open it in a browser.
- **Variation** `L04b-...`: respond with a different body depending on the path (`/` vs `/about`), and `400 Bad Request` if the request line is malformed.
- **Break it:** send the wrong `Content-Length` and watch `curl`. Type a request slowly in `nc` so it arrives in pieces: does your read loop cope?
- **Explain back:** How do you know the headers ended? How does the client know the body ended?
